# DQA 研发质量分析

先执行 `quality-analysis-core`，再应用本模块规则。

## 数据与口径

并列分析四类证据，不能相互替代：

1. 研发问题：评审、生产和现场阶段暴露及问题分类。
2. 设计评审：评审项目、评审成员参与、意见提出和更新日期。
3. ECN：变更数量、原因、创建人、产品部和物料代码。
4. 非BOM：申请数量、申请人、产品部和物料代码。

物料代码35开头的加工件按项目现有固定口径读取；分子每行计一项，分母只使用软件已经计算的加工件总数。不得由模型自行补算。

研发问题、ECN、非BOM、评审的统计周期和分母必须分别说明。数量多不自动等于风险高，还要看阶段逃逸、重复性、影响和门禁失效。

## 组织主线

依据研发组织映射和原始字段分析：

```text
公司 → 产品部 → TPM → PM → 研发工程师
```

公司和产品部报告可汇总到TPM；PM和研发工程师结论必须有对应字段。没有个人字段时不得使用TPM或产品部数据代替。

## 双重 Pareto

- 组织 Pareto：产品部、TPM；有完整字段时下钻PM和工程师。
- 机制 Pareto：问题分类、学科、评审/生产/现场阶段、ECN原因、加工件变更。
- 交叉 Pareto：高风险产品部/TPM×源头机制。

同时识别评审发现与后端暴露的差异。评审发现增加可能代表前端拦截增强，不能与生产或现场逃逸混为质量恶化。

## 风险与机制

沿“需求→方案→设计→评审→ECN/非BOM变更→验证→发布→生产/现场反馈”分析。重点检查需求与接口、评审知识是否到场、变更影响分析、BOM/图纸/软件版本一致性、加工件验证和剩余风险接受。

研发问题与ECN同期出现只构成关联线索；没有项目、物料、版本或人员证据时不得认定同源。

## 行动与输出

- 0—30天：锁定后端逃逸、重复问题和高风险变更，补齐临时门禁和影响分析。
- 31—60天：固化需求、设计评审、变更评审、版本绑定和加工件验证规则。
- 61—90天：验证生产/现场问题、重复ECN和非BOM加工件风险是否下降，回灌设计规则和评审清单。

正式报告按公司→产品部→TPM三级给管理结论；PM和工程师明细作为责任证据，由角色 Agent生成个人或管理范围报告。
