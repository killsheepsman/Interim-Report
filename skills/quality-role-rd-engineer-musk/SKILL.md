# 研发工程师个人质量闭环 · 决策版

先继承 `quality-analysis-core` 与 `quality-role-rd-engineer` 的数据边界。本 Skill 只改变分析与决策方式，不重算固定快照。

## 硬口径

- 研发质量问题是唯一质量结果；ECN、非 BOM 是工程活动，设计评审是正向过程证据，四者不得相加、共用分母或混入同一趋势和排名。
- 固定快照给出的数量、月份、排名、分子、分母、比例和映射必须原样采用，不得改写为“待核实”。只有输入确实缺失时才写待核实，并注明缺失字段、补核人和期限。
- 没有有效设计输出总量时不计算研发不良率。DQA 本人只取`责任人`或`工程师`；ECN 只取`创建人`；非 BOM 只取`申请人`；评审按`评审成员/提出人/更新日期`计数。管理者姓名只取确认映射。
- 模型不输出 JSON、代码、机器字段名或空章节。视觉契约由项目 Agent 用固定统计生成；图表必须放在对应章节并替换同源表格。

## 决策逻辑

第一屏先给一句判决：本期最应消除的一个主导失效机制、已证实基线、流出阶段/影响、现在必须作出的决定。不得把“设计问题”这种宽泛分类当根因，也不得用 ECN 数量代表质量差。

问题分类 Pareto 只说明集中度，不叫根因 Pareto。根据全部可用证据提出设计输出完整性、BOM/图纸/3D一致性、结构接口、边界工况、可维护性或发布门禁等机制；选出贡献最大或后果最重的 1 个瓶颈。证据不足时写成可检验假设，不得指责“粗心、意识差、能力不足”。

按以下顺序设计改进：质疑该步骤或需求为何存在；删除重复审批、重复报表和无效检查；简化为一个发布门禁；缩短验证周期；最后才自动化。会议、培训、提醒、补台账只能临时止血，不能作为永久关闭。

## 必须分析的数据

1. **质量结果**：问题总数、月/周趋势、评审/生产/售后阶段、类型 Pareto、严重度、重复、未关闭、逾期和客户流出。确定性趋势必须覆盖完整周期，零值保留；缺少分母时只展示问题数量，不生成不良率。
2. **ECN**：总数、原因、项目和加工件/标准件。固定分母齐全时，显示总体 ECN 比例、加工件比例、标准件比例及倍数，百分比保留两位；不得暴露 `ecnRate` 等内部字段。区分必要变更与设计错误、BOM漏做、重复变更等可避免变更，不要求无差别核验全部 ECN。
3. **非 BOM**：加工件和标准件分别展示，检查重复申请、转正式 BOM 和标准化沉淀，不自动判为质量问题。
4. **设计评审**：参与次数和有效改善项单独作为正向贡献；用“发布前拦截数、评审后生产/售后暴露数”判断有效性，出席本身不算贡献或关闭。
5. **排名**：采用固定排名及样本量，说明排序方向；本人必须出现并高亮。不得输出空的排名章节。

## 图表

- 月/周问题趋势：折线或柱形；有有效设计输出分母时才用数量柱形+不良率折线。
- 问题机制：Pareto柱形+累计折线。
- ECN：加工件与标准件的数量及比例用簇状条形图；非 BOM 构成用堆叠柱形图。
- 本人排名：簇状水平条形图，当前人员`focus: true`。

图表已表达的数据不再重复成表；问题证据和行动关闭条件保留表格。

## 最少行动闭环

只保留最关键的 1—3 项工程动作。至少一项必须明确选“3个新项目或5个高风险设计输出”做可逆的最小验证。指标固定为：样本覆盖率=完成门禁样本÷计划样本，目标100%；发布前检出率=发布前发现问题÷（发布前发现问题+后端再暴露问题），分母为0时标记不适用，目标100%；单项验证周期=提交验证至放行结论，试行目标≤5个工作日；后端再暴露数目标0项。不得用样本覆盖率冒充检出率，也不得用日历日期范围冒充单项验证周期。

每项只有一个 Owner，协同人另列。30、60、90天必须分别写从报告生成日计算出的`YYYY-MM-DD`日期，不得只写90天总截止日期；同时写基线、目标、交付物、证据、通过阈值、失败回退和复发重开条件。

历史证据补齐与永久防错分开。行动表是唯一待办来源，不再重复30/60/90天列表；不得把完成文档、开会、培训或检查全部 ECN 当作质量改善。

## 正式报告结构

1. 个人质量判决与当前决策
2. 质量结果概览；月度趋势、周度趋势和研发质量问题排名分别使用独立标题，排名结论只出现一次
3. 主导失效机制 Pareto 与典型证据
4. ECN、非 BOM 工程活动风险
5. 设计评审正向贡献与拦截效果
6. 1—3 项工程门禁及 30/60/90 天验证
7. PM/TPM 协调事项、数据限制和关闭条件

发布前核对：质量问题总数等于月度合计；已给趋势和排名不为待核实；活动量未混入质量结果；正文无空章节、机器字段和重复图表表格；每项行动可以判定通过或失败。
