# 组装人员个人质量闭环报告 · Musk版

## 视觉数据输出

正式报告必须兼容 skills/report-web-publisher 的网页呈现 Profile。内容结构要满足 chart-first：趋势、Pareto、排名、分布、闭环状态优先使用图表；责任、行动、证据、期限保留表格。

正式报告末尾必须遵循 skills/quality-analysis-core/references/report-visual-contract.md 输出 reportKind: "role" 的 REPORT_VISUAL_SPEC_JSON。设置 subject.scopeType: "direct"，图表只使用送检人字段识别本人；输出本人异常趋势、本人问题类型、本人排名和匹配考试主题，并将本人排名项标记 focus: true。

网页呈现 Profile 由渲染层负责，不在正文中写 CSS 类名、页面标记或任何机器元数据标题。正文只输出可读内容与证据链。

## 1. 角色边界

组装人员 Agent 报告只分析当前组装人员本人在统计周期内的 IPQC 送检记录。

组装人员的人员字段必须使用原始数据中的“送检人”。不得使用“检验人”“检验员”“判定人”或其他质量人员字段替代。送检人是组装责任对象，检验人员不是组装人员。

机长、交付经理和供应链经理只作为责任链汇报对象，不把其管理范围数据写成组装人员本人问题。

报告要区分：

- 本人直接质量结果。
- 本人执行过程暴露。
- 设备、材料、工艺或标准造成的系统性原因。
- 需要机长、交付经理或供应链经理处理的管理事项。

不能因为发现异常就直接判断本人态度、能力或培训不足，必须有过程证据。

## 2. 数据源与字段口径

只使用 IPQC 原始数据和固定统计引擎结果。每条证据保留日期、送检人、工坊、机长、交付经理、供应链经理、项目/产品、数量、异常数量、问题类型和闭环状态。

### 关键指标

- 送检批次/记录数：本人送检记录数量，反映工作量，不直接代表质量好坏。
- 送检数量：本人送检件数，作为密度分母时使用软件固定口径。
- 异常数量：异常件或异常数量，作为结果暴露量。
- 问题记录数：问题明细行数量，不等同于异常数量。
- 异常密度/异常率：严格使用项目现有统计定义；不能用异常记录数冒充异常率。
- 问题类型：按原始字段归一化，保留 TOP 类型和明细证据。
- 重复问题：同一问题类型、工序、项目或相同证据在规定周期内再次出现。
- 关闭状态：已纠正、待复检、已验证关闭、逾期或无证据。

当分母、日期、问题类型或关闭状态缺失时，标记“部分数据”或“待核实”，不得自行补算。

## 3. 马斯克式分析规则

### 3.1 先找瓶颈

先回答三个问题：

1. 本周期最主要的失效点是什么。
2. 它是否是重复出现的真正瓶颈。
3. 哪一个动作最能压缩返工、复发和等待时间。

只保留能解释大部分问题的少数瓶颈，不写泛泛的“加强培训”“提高意识”。

### 3.2 第一性原理

把“结果”与“原因假设”分开。

- 结果必须来自数据。
- 根因可以是假设，但每个假设都要带验证动作、责任人和期限。
- 没有证据的根因写“待核实”，不要包装成结论。

### 3.3 执行压力

每一项改善都必须写清：

- 责任人
- 截止时间
- 验收指标
- 复查证据
- 失效回退条件

如果一个动作不能减少返工、缩短闭环或降低复发，就不要把它写成主动作。

### 3.4 成本与时间

优先识别会消耗大量返工、重复送检和现场等待的环节。不要让低价值描述占据报告篇幅。

## 4. 数据审计

生成报告前检查：

1. 是否存在“送检人”字段，姓名是否已去空格、统一别名和去重。
2. 是否错误读取了检验人员字段；检验人员不得进入组装人员名单。
3. 统计周期是否一致，日期是否落在当前筛选范围内。
4. 送检数量、异常数量和问题记录数是否被重复计算。
5. 同一文件是否重复导入，同一记录是否重复出现。
6. 机长、交付经理、供应链经理映射是否来自供应链映射表。
7. 无法映射的工坊或责任链是否单独显示。

所有结论标记证据等级：

- 已证实：原始 IPQC 记录直接支持。
- 合理推断：多个记录呈现同一模式，但仍需现场确认。
- 待核实：现有数据无法确认，必须生成验证待办。

## 5. 报告结构

### 一、本人质量结果总览

显示姓名、统计年份和日期范围、工坊、责任链、送检批次、送检数量、异常数量、问题记录数、异常密度/异常率、重复问题、未关闭和逾期问题、数据更新时间和数据完整性。送检量和质量风险要分开展示。

### 二、过程暴露分析

按“作业标准 → 组装执行 → 自检 → 送检 → 异常反馈 → 纠正 → 复检关闭”追踪，区分本人执行偏差与标准、设备、材料、工装或接口异常。

### 三、问题类型与 Pareto

按问题类型、工序、项目/产品和月份展示 TOP 问题类型、数量、重复次数、状态和异常密度。问题类型 Pareto、月份趋势和问题状态优先用图表，样本不足时只展示事实。

### 四、个人风险排名

排名图表嵌入正式报告，当前人员用红色五角星、红色姓名和红色数据条突出显示。排序优先看异常密度、重复问题、未关闭/逾期、高严重度和影响范围，送检量只作工作量辅助。

### 五、根因证据

按场景与标准、流程与接口、设备与材料、决策与证据、能力与责任五层分析。没有培训记录、操作观察或重复行为证据时，不得写培训不足、粗心或质量意识差。

## 6. 责任链汇报

本人负责执行最新版作业指导书、首件和自检、隔离反馈、纠正复检并留存证据。向机长汇报重复异常、标准设备工装材料问题和权限外事项。向交付经理或供应链经理升级多人员共享问题、工坊资源问题和外部加工问题。管理者数据只能作为上报背景，不能改写成本人直接责任。

## 7. 知识考试

只根据本人真实问题类型匹配题目。题库缺失时显示“暂无对应题库”，不得随机出题。报告附答题链接，并在下次报告中显示完成状态、得分、错题类型和是否转化为过程改进。考试通过不能单独证明问题关闭，必须有复检或现场验证证据。

## 8. 30/60/90 天改善行动

每项行动必须包含责任人、期限、验证指标、证据位置、失效回退和关闭条件。

- 0—30 天：止血。核查本人 TOP 3 异常，隔离重复问题，补齐自检、反馈和复检证据。
- 31—60 天：固化。把关键检查点、工装防错、首件和自检固化到班组控制清单。
- 61—90 天：验证。验证同类异常是否复发，确认异常密度和重复问题下降，并将有效措施固化到作业指导书、题库和现场审核。

培训、提醒和“加强意识”不能单独作为永久措施，必须绑定到标准、物理防错、参数锁定、检验规则或现场验证。

## 9. 结论输出格式

按“分析结论 → 风险判断 → 改善措施 → 待办事项”输出，同时保留“结果—过程—根因—责任—行动”证据链。

## 10. 禁止事项

- 不得使用检验人、检验员或判定人字段识别组装人员。
- 不得用管理者排名代替本人排名。
- 不得把送检数量或异常发现量直接当作异常率。
- 不得在没有证据时判断培训、态度、粗心或能力原因。
- 不得虚构问题类型、数量、严重度、根因、考试结果或关闭结果。
- 不得跨统计周期混用数据。
- 不得把报告生成、培训完成或表格填写完成当作问题已关闭。
- 不得在最终可读报告里展示内部证据编号、机器元数据标题或规则编号。
