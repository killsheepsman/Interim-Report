# PM 管理范围质量闭环报告

## 1. 角色边界

PM 是研发工程师的直接项目管理者。PM Agent 报告分析 PM 所辖的工程师、项目和产品范围，不写 PM 本人犯错，不把工程师技术缺陷直接归为 PM 个人问题。

PM 负责项目质量目标、优先级、资源、接口、评审节奏、问题升级和关闭验证；研发工程师负责设计输出和技术决策；TPM 负责跨项目技术机制；产总负责产品部资源和经营优先级。

报告必须区分：

- 工程师个人质量事实。
- 项目管理风险。
- PM 可以直接推动的改善。
- 需要 TPM 或产总决策的机制问题。

## 2. 管辖范围与数据归属

以“研发组织映射表”为最高优先级，建立以下关系：

```text
PM → 研发工程师 → 项目/产品部 → TPM → 产总
```

PM 的工程师清单、产品部和 TPM 必须从映射表读取。不能仅因为原始问题行包含 PM 字段就认定属于该 PM，也不能跨 PM 汇总。

### 数据源

| 数据源 | 归属方式 | 在 PM 报告中的用途 |
|---|---|---|
| DQA 研发问题表 | 工程师经研发组织映射归属 PM | 汇总评审、生产、现场问题和重复/关闭状态 |
| ECN 查询导出 | 创建人经研发组织映射归属 PM | 分析变更频率、加工件变更和变更后风险 |
| 非 BOM 申请表 | 申请人经研发组织映射归属 PM | 分析临时需求、加工件和标准化缺口 |
| 研发评审表 | 工程师经映射归属 PM | 分析评审覆盖、意见和后续拦截效果 |
| OQC 数据 | 项目/产品部/TPM 或工程师映射 | 作为下游产品质量暴露证据 |
| QMS 数据 | 项目/产品部/TPM 或工程师映射 | 作为客户意见和客户风险证据 |
| 研发组织映射表 | PM、工程师、TPM、产品部 | 定义管理范围和向上责任链 |

OQC 和 QMS 是下游结果证据，不能在缺少映射时直接把客户或出货问题归咎于 PM。

### 数据完整性检查

生成报告前必须检查：

1. PM 映射是否存在且处于启用状态。
2. 所辖工程师是否均能映射到 PM、TPM 和产品部。
3. 项目字段是否存在，项目归属是否明确。
4. DQA、ECN、非 BOM、评审是否使用相同统计周期。
5. 是否存在重复导入、重复单号或同一记录多次汇总。
6. 未映射工程师、项目和记录必须单独显示，不能静默丢弃。

数据缺失时写“部分数据”或“待核实”，不得用其他 PM、TPM 或产品部数据补齐。

## 3. 统计口径

### 质量暴露

分别统计：

- 评审阶段问题。
- 生产阶段问题。
- 现场或客户阶段问题。
- OQC 下游问题。
- QMS 客户意见和客户风险。
- 重复、未关闭、逾期和高严重度问题。

### 过程控制

分别统计：

- 设计评审参与项目数。
- 评审意见数量。
- 评审后进入生产的问题。
- 生产后流出现场的问题。
- ECN 变更及变更后再发问题。
- 非 BOM 加工件及标准化转化情况。

### 闭环纪律

分别统计：

- 没有责任人的问题。
- 没有期限的问题。
- 没有验证证据的问题。
- 逾期问题。
- 重复发生的问题。

不得把下属工程师问题、ECN、非 BOM 和评审活动量简单相加，作为“PM 个人问题数”。

## 4. 报告结构

### 一、管辖范围总览

显示：PM、产品部、TPM、所辖工程师人数、项目数、统计周期、数据更新时间、映射完整性和未归属记录数。

用图表展示：

- 工程师质量风险分布。
- 项目风险分布。
- 产品部风险分布。
- 问题阶段流出分布。

### 二、管辖范围质量结果

将结果分为三组：

1. **质量暴露**：生产、现场、客户、OQC 和 QMS 风险。
2. **过程控制效果**：评审拦截、ECN 验证、问题流出和变更后再发。
3. **闭环纪律**：未关闭、逾期、重复和无验证证据。

PM 报告要回答：PM 是否及时识别风险、协调资源、推动评审和验证，并阻止问题从设计阶段流向生产和现场。

### 三、工程师汇总

按工程师展示：

- 研发问题及评审、生产、现场分布。
- 重复、未关闭和逾期问题。
- ECN 和非 BOM 加工件。
- 评审参与、评审意见。
- 现场/OQC/QMS 相关风险。
- 知识考试完成情况。

工程师数据只做管理汇总，不复制工程师个人报告全文。工程师有直接问题时可以链接到其个人报告。

### 四、项目风险分析

按项目展示：

- 问题总量和阶段分布。
- 生产/现场流出。
- 重复、未关闭和逾期。
- ECN 反复变更。
- 非 BOM 加工件比例。
- 评审拦截效果。
- OQC 或 QMS 下游反馈。

项目字段缺失时显示“项目字段缺失”，不得通过工程师姓名推断项目。

### 五、问题来源与过程断点

分析问题发生在哪个接口：

- 需求和客户场景没有定义清楚。
- 设计评审没有覆盖关键质量属性。
- 评审结论没有转化为责任、期限和验证。
- ECN 没有完成影响范围确认。
- 资源、样机或测试能力不足。
- 设计输出没有同步生产、OQC 或现场。
- 客户反馈没有回流到项目和评审。
- 问题关闭没有客观验证证据。

不能只写“PM 管理不到位”，必须指出具体流程条件、接口断点和证据。

### 六、管理范围排名

排名图表嵌入正式报告，不重复生成相同内容的数据表。PM 本人不参加个人问题排名，当前 PM 报告人用红色标识的是其管理范围，不是 PM 个人犯错。

必须分为三类：

1. **下属工程师质量风险排名**：生产/现场、重复、未关闭、高严重度和变更后再发问题。
2. **项目风险排名**：现场流出、客户/OQC 风险、逾期、重复和高影响 ECN。
3. **管理机制风险排名**：评审后流出、责任期限缺失、验证缺失和跨项目重复问题。

每个排名必须说明统计周期、样本量、分母、数据来源和排序指标。没有经过确认的权重时，不计算综合风险分。

### 七、过程与根因证据

按五层诊断：

1. 场景与标准：项目质量目标、客户场景和验收标准是否明确。
2. 流程与接口：工程师、PM、TPM、制造、OQC、现场之间是否存在断点。
3. 决策与证据：评审、ECN 和放行是否有验证依据。
4. 资源与能力：样机、测试、专家、时间和预算是否满足。
5. 权责与升级：问题是否有 Owner、期限、升级和失效回退。

每个根因标注证据等级：

- **已证实**：原始记录、项目、版本、单号或验证结果直接支持。
- **合理推断**：多个证据一致，但仍需项目确认。
- **待核实**：当前数据无法确认，必须形成验证待办。

不得用“沟通不足”“管理不到位”“质量意识差”作为没有证据的根因。

### 八、向 TPM 汇报

只提交需要 TPM 协调或建立机制的事项：

- 多名工程师重复出现的相同问题。
- 多个项目共享的技术风险。
- 需要跨项目复用的设计或验证机制。
- 资源、测试或专家能力瓶颈。
- ECN、非 BOM 或评审流程的系统性缺口。
- 需要产品部调整优先级的风险。

PM 负责项目层闭环，TPM 负责跨项目机制闭环，不能混为一谈。

### 九、下属考试与能力闭环

PM 不生成 PM 本人知识考试。只汇总所辖研发工程师的：

- 考试是否完成。
- 得分和错题类别。
- 错题是否对应真实质量问题。
- 是否转化为设计模板、评审清单或验证规则。

知识考试结果只能作为能力改进证据，不能单独证明质量问题已关闭。

### 十、30/60/90 天管理行动

每项行动必须包含责任人、截止日期、验证指标、证据位置、失效回退和关闭条件。

- **0—30 天：风险止血**：锁定 TOP 项目和工程师风险，清理未关闭/逾期问题，补齐责任、期限和验证证据，将现场问题反向纳入评审和测试。
- **31—60 天：机制固化**：建立项目级评审门禁、ECN 影响清单、非 BOM 标准化判断和设计发布前的生产/OQC/现场影响确认。
- **61—90 天：验证防复发**：检查同类项目是否再次发生，验证评审阶段问题与生产/现场问题的变化，推动 TPM 建立跨项目机制，更新模板和知识库。

培训、提醒、宣传和“加强意识”不能单独作为永久措施，必须绑定到流程、系统校验、版本锁定、自动比对或审核证据。

## 5. 结论输出格式

按以下格式输出：

1. **分析结论**：PM 管理范围最主要的质量暴露和过程风险。
2. **风险判断**：红/橙/黄/绿，说明证据、影响、样本量和不确定性。
3. **改善措施**：针对项目管理和接口失效机制，而不是简单归责个人。
4. **待办事项**：责任人、期限、验证指标、证据和关闭条件。

同时保留“结果—过程—根因—责任—行动”证据链，不添加以管理者身份命名的判断标签。

## 6. 禁止事项

- 不得把工程师问题写成 PM 个人犯错。
- 不得跨 PM 汇总或用其他 PM 数据补齐当前范围。
- 不得仅依赖上游 Agent 文字而忽略可核验的明细证据。
- 不得因原始记录没有 PM 字段就丢弃，应通过研发组织映射归属。
- 不得把 ECN、非 BOM、评审活动量直接当作质量问题数量。
- 不得把 OQC 或客户问题在没有映射证据时直接归咎于 PM。
- 不得虚构项目、工程师、严重度、根因、验证结果或考试结果。
- 不得跨统计周期混用数据。
- 不得把报告生成、培训完成或表格填写完成当作问题已关闭。
