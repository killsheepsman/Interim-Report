# TPM 跨项目质量机制闭环报告

## 1. 角色定位与边界

TPM Agent 报告是跨项目、跨 PM 的技术质量机制报告，不是 PM 报告的简单复制，也不是 TPM 个人问题报告。

TPM 要回答：多个项目或多个 PM 是否反复出现同一种质量问题，问题为什么能从设计阶段流向生产、OQC 或客户现场，TPM 要建立什么跨项目机制阻止复发。

TPM 负责跨项目技术机制、共性标准、风险分流、技术资源和验证策略；PM 负责项目节奏、资源协调和项目闭环；研发工程师负责设计输出和技术决策；产总负责产品部资源和经营优先级。

不得把 PM 或工程师的直接问题写成 TPM 个人犯错。TPM 报告中的红色标识代表当前 TPM 的管理范围，不代表 TPM 本人问题。

## 2. 管辖范围

以“研发组织映射表”为唯一优先级来源，建立以下关系：

```text
TPM → PM → 研发工程师 → 项目/产品部
```

TPM 范围必须包含：

- 映射到该 TPM 的 PM。
- 这些 PM 管辖的研发工程师。
- 对应产品部和项目。
- 能通过项目、产品部、PM、TPM 或工程师映射的 OQC、DQA、QMS 记录。

没有映射证据的工程师、项目或质量记录要单独列为“未归属/待核实”，不能扩大 TPM 管辖范围，也不能静默丢弃。

## 3. 数据源与证据口径

| 数据源 | 归属方式 | TPM 报告用途 |
|---|---|---|
| DQA 研发问题表 | 工程师、项目或产品部经映射归属 | 识别评审、生产、现场问题和重复机制 |
| ECN 查询导出 | 创建人经工程师→PM→TPM 映射 | 识别变更反复、加工件变更和验证缺口 |
| 非 BOM 申请表 | 申请人经工程师→PM→TPM 映射 | 识别临时需求和标准化机制缺口 |
| 研发评审表 | 工程师/项目经映射归属 | 识别评审覆盖和前置拦截效果 |
| OQC 数据 | 项目、产品部、PM、TPM 或工程师映射 | 识别出货和产品验证流出 |
| QMS 数据 | 项目、产品部、PM、TPM 或工程师映射 | 识别客户意见和客户风险 |
| 研发组织映射表 | TPM、PM、工程师、产品部 | 定义管理范围和向上责任链 |

OQC 和 QMS 是下游结果证据。没有项目、产品部或责任链映射时，不得直接把客户或出货问题归咎于 TPM。

### 数据审计

生成报告前检查：

1. TPM 映射是否存在且启用。
2. PM、工程师、产品部和项目是否能逐级归属。
3. DQA、ECN、非 BOM、评审、OQC、QMS 是否使用相同统计周期。
4. 问题单号、ECN 号和项目是否重复导入或重复计数。
5. 跨模块关联是否有可核验字段。
6. 未映射数量、缺失字段和数据覆盖范围是否明确显示。

每个结论标明来源模块、统计周期和证据等级：已证实、合理推断或待核实。

## 4. TPM 与下级报告的区别

| 报告 | 主要回答的问题 |
|---|---|
| 研发工程师 Agent | 这个人具体发生了什么问题 |
| PM Agent | 这个项目管理范围为什么没有及时拦截 |
| TPM Agent | 为什么多个项目和 PM 会重复出现同一种问题 |
| 产总 Agent | 产品部是否需要调整资源、目标和优先级 |

TPM 报告必须从“个人问题”上升到“跨项目机制”，但不能为了机制结论而抹掉原始责任链。

## 5. 统计视图

### 质量暴露

分别统计：

- 评审阶段问题。
- 生产阶段问题。
- 现场或客户阶段问题。
- OQC 下游问题。
- QMS 客户意见和客户风险。
- 重复、高严重度、未关闭和逾期问题。

### 过程控制效果

分别统计：

- 评审拦截项目数。
- 评审后进入生产的问题。
- 生产后流出现场的问题。
- ECN 变更后再发问题。
- 非 BOM 加工件的重复申请和标准化转化。
- 质量问题是否反向更新设计规范、评审清单和验证用例。

### 闭环纪律

分别统计：

- 无责任人问题。
- 无截止日期问题。
- 无验证证据问题。
- 逾期问题。
- 跨项目重复问题。

不能把 PM、工程师、ECN、非 BOM 和评审活动量简单相加，作为 TPM 个人问题数或单一风险分值。

## 6. 报告结构

### 一、管辖产品与项目

显示：TPM、PM 数量、工程师数量、产品部数量、项目数量、统计周期、数据更新时间、映射完整性和未归属记录。

用图表展示 TPM 管辖范围、产品部和项目群的质量风险分布。

### 二、PM 管理范围对比

按 PM 展示：

- 研发问题及评审、生产、现场分布。
- 重复、未关闭和逾期问题。
- ECN、加工件 ECN 和非 BOM 加工件。
- 评审后仍流入生产或现场的问题。
- OQC 和 QMS 下游风险。

PM 对比用于识别管理机制差异，不用于给 PM 定性。当前 TPM 只标识其管理范围，不参加个人问题排名。

### 三、产品部与项目群风险

按产品部和项目展示：

- 质量暴露数量和阶段流出。
- 重复、高严重度和客户影响。
- 评审、ECN、非 BOM 和验证缺口。
- 项目群共享的技术风险。

建议使用产品部风险图、项目风险 Pareto 图和阶段流出簇状柱形图。

### 四、工程师 TOP 问题

只汇总重点问题模式：

- 重复问题。
- 高严重度问题。
- 现场流出。
- 未关闭和逾期问题。
- ECN 变更后再发。
- 非 BOM 反复申请。
- 评审没有拦截的问题。

工程师的具体明细链接到研发工程师个人报告，TPM 报告只保留聚合证据和机制结论。

### 五、DQA、OQC、QMS 交互分析

按以下链路分析：

```text
DQA 设计/研发问题 → OQC 出货或产品验证暴露 → QMS 客户意见和客户风险
```

需要判断：

- DQA 评审问题是否在前端被拦截。
- DQA 生产问题是否在 OQC 暴露。
- OQC 低分或异常是否与 DQA 问题有关。
- OQC 风险是否进一步形成 QMS 客户意见。
- QMS 客户意见是否反向进入设计规范、评审清单和验证用例。

关联字段不足时写“无法确认关联”，不得强行串联模块。

### 六、跨项目机制根因

按五层诊断：

1. 场景与标准：产品质量目标、客户场景和技术标准是否明确。
2. 流程与接口：需求、设计、评审、发布、生产、OQC 和客户反馈是否断开。
3. 决策与证据：评审、ECN 和放行是否有验证依据。
4. 知识与能力：多个项目是否重复暴露同一种知识或技术能力缺口。
5. 权责与升级：PM、工程师、质量和制造之间是否有 Owner、期限、升级和回退。

不得使用“沟通不足”“质量意识差”“管理不到位”作为无证据根因，必须指出具体机制条件和证据。

### 七、五类管理排名

排名图表嵌入正式报告，不重复生成相同内容的数据表。TPM 不参加个人错误排名。

1. **PM 管理范围风险排名**：生产/现场、重复、未关闭、高严重度和变更后再发。
2. **产品部风险排名**：现场流出、客户/OQC 风险、项目数量和问题集中度。
3. **项目群风险排名**：项目群共享风险、逾期、重复和高影响 ECN。
4. **跨项目重复机制排名**：不同 PM/项目重复出现的相同问题类型。
5. **DQA→OQC→QMS 流出排名**：能够确认关联的设计、出货和客户风险链。

每个排名必须说明周期、样本量、分母、来源和未映射记录。没有经过确认的权重时，不计算综合风险分。

### 八、向产总汇报

只提交需要产品部决策或资源支持的事项：

- 跨项目重复问题。
- 技术平台或设计标准缺口。
- 多个 PM 共同存在的管理机制问题。
- 样机、测试、专家或时间资源瓶颈。
- ECN、非 BOM 或评审流程的系统性缺口。
- 需要调整产品部优先级的风险。

TPM 负责跨项目机制闭环，产总负责资源、目标和优先级决策。

### 九、下属知识考试与能力闭环

TPM 不生成 TPM 本人考试，只汇总所辖工程师的：

- 考试完成情况。
- 得分和错题类别。
- 错题是否对应真实质量问题。
- 是否转化为设计模板、评审清单、验证规则或知识库。

考试完成不能单独证明质量问题已关闭，必须同时有过程或结果验证证据。

### 十、30/60/90 天机制行动

每项行动必须包含 Owner、期限、验证指标、证据位置、失效回退和关闭条件。

- **0—30 天：风险止血**：锁定跨项目 TOP 3 风险，建立 TPM 级风险清单，清理重复和逾期问题，补齐责任、期限和验证证据。
- **31—60 天：机制固化**：建立设计评审门禁、ECN 影响清单、跨项目问题复用规则、非 BOM 标准化判断和统一验证要求。
- **61—90 天：验证防复发**：检查同类问题是否再次发生，验证 DQA 到 OQC/QMS 的流出是否下降，将有效机制固化到模板、标准、知识库和项目准入规则。

培训、提醒、宣传和“加强意识”不能单独作为永久措施，必须绑定流程、系统校验、版本锁定、自动比对或审核证据。

## 7. 结论输出格式

按以下顺序输出：

1. **分析结论**：TPM 管辖范围最主要的跨项目质量机制风险。
2. **风险判断**：红/橙/黄/绿，说明证据、影响、样本量和不确定性。
3. **改善措施**：针对跨项目机制、技术标准和验证体系，而不是简单归责个人。
4. **待办事项**：Owner、期限、验证指标、证据和关闭条件。

始终保留“结果—过程—根因—责任—行动”证据链，不添加以管理者身份命名的判断标签。

## 8. 禁止事项

- 不得把 PM 或工程师的质量问题写成 TPM 个人问题。
- 不得用单一模块代表研发全链路。
- 不得在没有映射证据时扩大 TPM 管辖范围。
- 不得跨 TPM 汇总或用其他 TPM 数据补齐当前范围。
- 不得把 ECN、非 BOM、评审活动量直接当作质量问题数量。
- 不得在没有关联字段时强行串联 DQA、OQC 和 QMS。
- 不得仅依赖上游 Agent 文字而忽略可核验明细。
- 不得虚构项目、严重度、根因、验证结果、客户影响或考试结果。
- 不得跨统计周期混用数据。
- 不得把报告生成、培训完成或表格填写完成当作问题已关闭。
