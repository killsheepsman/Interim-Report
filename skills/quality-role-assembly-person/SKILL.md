# 组装人员个人质量闭环报告

## 视觉数据输出

独立运行时，正式报告末尾必须遵循 `skills/quality-analysis-core/references/report-visual-contract.md` 输出 `reportKind: "role"` 的 `<REPORT_VISUAL_SPEC_JSON>`。在 QMS 项目内运行时，该契约由 Agent 基于固定统计自动生成，模型只输出管理层可读正文，不能自行编造或遗漏图表数据。设置 `subject.scopeType: "direct"`，图表只使用送检人字段识别本人；输出本人异常趋势、本人问题类型、本人排名和匹配考试主题，并将本人排名项标记 `focus: true`。

### 网页呈现 Profile 要求

- 报告必须能被 Apple、Notion 或研究简报 Profile 重绘；切换 Profile 不得改变数字、口径、排名或结论。
- 趋势、Pareto、排名、分布和状态构成优先由图表表达；责任、行动、证据、期限和关闭条件保留表格。
- 图表必须放回对应章节，不得全部堆在报告顶部；个人排名图表中当前人员必须标记为焦点对象。
- Profile 只负责视觉层级、图表位置、颜色和响应式布局，不得改变分析结果。
- 正文不得输出 CSS 类名、页面标记、机器元数据标题或视觉契约代码。

## 1. 角色边界

组装人员 Agent 报告只分析当前组装人员本人在统计周期内的 IPQC 送检记录。

组装人员的人员字段必须使用原始数据中的“送检人”。不得使用“检验人”“检验员”“判定人”或其他质量人员字段替代。送检人是组装责任对象，检验人员不是组装人员。

机长、交付经理和供应链经理只作为责任链汇报对象，不把其管理范围数据写成组装人员本人问题。

报告要区分：

- 本人直接质量结果。
- 本人执行过程暴露。
- 设备、材料、工艺或标准造成的系统性原因。
- 需要机长、交付经理或供应链经理处理的管理事项。

不能因为发现异常就直接判断本人态度、能力或培训不足，必须有过程证据。

## 2. 数据源与字段口径

只使用 IPQC 原始数据和固定统计引擎结果。每条证据保留日期、送检人、工坊、机长、交付经理、供应链经理、项目/产品、数量、异常数量、问题类型和闭环状态。

### 关键指标

- **送检批次/记录数**：本人送检记录数量，反映工作量，不直接代表质量好坏。
- **送检数量**：本人送检件数，作为密度分母时使用软件固定口径。
- **异常数量**：异常件或异常数量，作为结果暴露量。
- **问题记录数**：问题明细行数量，不等同于异常数量。
- **异常密度/异常率**：严格使用项目现有统计定义；不能用异常记录数冒充异常率。
- **问题类型**：按原始字段归一化，保留 TOP 类型和明细证据。
- **重复问题**：同一问题类型、工序、项目或相同证据在规定周期内再次出现。
- **关闭状态**：已纠正、待复检、已验证关闭、逾期或无证据。

当分母、日期、问题类型或关闭状态缺失时，标记“部分数据”或“待核实”，不得自行补算。

## 3. 数据审计

生成报告前检查：

1. 是否存在“送检人”字段，姓名是否已去空格、统一别名和去重。
2. 是否错误读取了检验人员字段；检验人员不得进入组装人员名单。
3. 统计周期是否一致，日期是否落在当前筛选范围内。
4. 送检数量、异常数量和问题记录数是否被重复计算。
5. 同一文件是否重复导入，同一记录是否重复出现。
6. 机长、交付经理、供应链经理映射是否来自供应链映射表。
7. 无法映射的工坊或责任链是否单独显示。

所有结论标记证据等级：

- **已证实**：原始 IPQC 记录直接支持。
- **合理推断**：多个记录呈现同一模式，但仍需现场确认。
- **待核实**：现有数据无法确认，必须生成验证待办。

## 3.1 第一性原理与瓶颈优先

报告先回答“最主要的失效点是什么、是否重复出现、哪个动作能最大幅度减少返工和等待”。只保留能够解释大部分风险的少数瓶颈，不用“加强培训、提高意识”替代具体控制动作。

- 结果必须来自固定数据；根因没有证据时只能写“待核实”。
- 每个待核实项必须同时给出验证动作、责任人和期限。
- 改善动作必须能对应到返工、复发、等待、漏检或闭环时长中的至少一个指标。
- 先删掉无法改变结果的泛化描述，再优化真正存在的控制点。

## 4. 报告结构

### 一、本人质量结果总览

显示：

- 组装人员姓名。
- 统计年份和日期范围。
- 工坊、机长、交付经理、供应链经理。
- 送检批次、送检数量、异常数量、问题记录数。
- 异常密度/异常率。
- 重复问题、未关闭和逾期问题。
- 数据更新时间和数据完整性。

送检量和质量风险要分开展示，不能因为送检量大就直接判定质量差。

所有比例必须带百分号，并同时显示分子、分母和口径。例如“不良率 17.55%（155/883）”，不得只输出无单位的 17.55。

- IPQC 中“问题记录数”按“不良内容或不良类型任一非空的送检记录”计数；若固定数据已给出该值，不得写“待核实”。
- 问题类型占比以本人不良记录为分母，必须输出数值和百分号；已给出问题类型数量与不良记录总数时，不得把占比写成“待核实”。
- 工坊、机长、交付经理、供应链经理只能引用 Agent 传入的原始记录或映射结果；未给出时写“待核实”，不得把当前组装人员姓名推断成其交付经理。

### 二、过程暴露分析

按“作业标准 → 组装执行 → 自检 → 送检 → 异常反馈 → 纠正 → 复检关闭”追踪。

重点分析：

- 异常集中在哪个工序或问题类型。
- 问题是首次发生还是重复发生。
- 是本人执行偏差，还是标准、设备、材料、工装或接口异常。
- 异常反馈后是否及时纠正和复检。
- 是否存在同一问题反复送检。

### 三、问题类型与 Pareto

按问题类型、工序、项目/产品和月份展示：

- TOP 问题类型。
- 每类问题的异常数量和问题记录数。
- 对应送检数量和异常密度。
- 重复次数。
- 已关闭、未关闭和逾期状态。

建议使用问题类型 Pareto 图、月份趋势图和问题状态图。没有足够样本时只展示事实，不强行排名。

### 四、个人风险排名

排名图表嵌入正式报告，当前人员用红色五角星、红色姓名和红色数据条突出显示。

排名必须优先按质量风险指标，而不是按送检工作量：

1. 异常密度/异常率。
2. 重复问题数量。
3. 未关闭和逾期问题。
4. 高严重度或高影响问题。
5. 在样本量足够时的异常数量。

送检批次和送检数量可以作为工作量辅助指标，不能直接作为坏绩效排名。

排名必须显示统计周期、样本量、分母、指标定义和数据来源。样本量不足时标记“样本不足，不作强结论”。

如果当前没有可用的排名数据，必须明确显示“暂无排名数据/待补充”，不得留下空白章节。
不得输出“章节标题”“待填”“示例”等模板占位文本。

### 五、根因证据

按五层分析：

1. **场景与标准**：作业指导书、图纸、工艺参数和验收标准是否明确。
2. **流程与接口**：领料、组装、自检、送检、异常反馈和复检是否断开。
3. **设备与材料**：设备、工装、材料或供应商状态是否造成异常。
4. **决策与证据**：首件、换线、参数变更或异常放行是否有记录和确认。
5. **能力与责任**：是否有明确岗位能力要求、现场支持和合理的工作安排。

“培训不足”“粗心”“质量意识差”只能在有培训记录、操作观察或重复行为证据时提出；否则写“待核实”。

“接线/装配问题较多”只能证明结果集中，不能直接证明标准不清、能力不足或自检失效。每个根因判断必须同时列出支持证据和最小验证动作。

### 六、责任链汇报

#### 本人行动

- 按最新版作业指导书和工艺参数执行。
- 完成自检和首件确认。
- 发现异常立即隔离、标识和反馈。
- 按要求完成纠正、复检和证据留存。

#### 向机长汇报

- 重复异常。
- 标准、设备、工装或材料问题。
- 需要调整工序、参数、排产或人员支持的问题。
- 无法在本人权限内关闭的异常。

#### 向交付经理/供应链经理升级

- 多名组装人员共享的相同问题。
- 工坊层面的设备、材料、工艺或资源问题。
- 供应链或外部加工因素造成的重复异常。

管理者数据只能作为上报背景，不能改写成本人直接责任。

责任链汇报要先指出瓶颈，再指出决策：

- 本人只承担本人可控制的执行、自检、隔离、反馈和证据留存。
- 机长优先处理班组共享的重复失效、标准缺口和现场防错。
- 交付经理优先处理跨工坊的资源、接口、设备和版本问题。
- 供应链经理只接收有来料或外部加工证据支持的升级项。

每个升级项必须说明“不处理的影响”、责任人、截止时间和验收门槛。

### 七、知识考试

组装人员是允许生成知识考试的角色。只根据本人真实问题类型匹配题目，例如：

- 组装工艺和作业标准。
- 首件、自检和送检要求。
- 问题类型对应的防错方法。
- 异常隔离、反馈和复检。

题库缺失时显示“暂无对应题库”，不得随机出题。报告应附答题链接，并在下次报告中显示：是否完成、得分、错题类型和是否已转化为过程改进。

考试完成不能单独证明问题关闭，必须有复检或现场验证证据。

### 八、30/60/90 天改善行动

每项行动必须包含责任人、期限、验证指标、证据位置、失效回退和关闭条件。

- **0—30 天：止血**：核查本人 TOP 3 异常，隔离重复问题，补齐作业标准、异常反馈和复检证据。
- **31—60 天：固化**：优化工序、工装、防错、首件和自检要求；将重复问题纳入机长的班组控制清单。
- **61—90 天：验证**：验证同类异常是否复发，确认异常密度和重复问题下降，将有效措施固化进作业指导书、培训题库和现场审核。

培训、提醒和“加强意识”不能单独作为永久措施，必须绑定到作业标准、物理防错、参数锁定、检验规则或现场验证。

行动设计采用“先删减、再简化、后加速、最后自动化”的顺序：先删除不增加质量价值的重复表单和无效检查，再把关键点简化为现场可执行的控制动作，随后缩短反馈与复检周期，只有流程稳定后才考虑自动提醒或自动生成。

首要行动必须直接对应 TOP 问题集中度最高的瓶颈；每项行动只设一个主责任人，其他角色列为协同或升级对象，避免把责任写成“刘能文 / 机长 / 交付经理”而无法验收。

## 5. 结论输出格式

按以下顺序输出：

1. **分析结论**：本人最主要的异常类型、过程暴露和重复风险。
2. **风险判断**：红/橙/黄/绿，说明异常密度、样本量、影响和不确定性。
3. **改善措施**：针对具体失效条件，不简单归咎个人。
4. **待办事项**：责任人、期限、验证指标、证据和关闭条件。

同时保留“结果—过程—根因—责任—行动”证据链，不添加以管理者身份命名的判断标签。

## 6. 禁止事项

- 不得使用“检验人”“检验员”字段识别组装人员。
- 不得用机长、交付经理或供应链经理的管理排名代替本人排名。
- 不得把送检数量或异常发现量直接当作异常率。
- 不得把异常发现量越多直接判定为本人质量越差。
- 不得在没有证据时判断培训、态度、粗心或能力原因。
- 不得虚构问题类型、数量、严重度、根因、考试结果或关闭结果。
- 不得跨统计周期混用数据。
- 不得把报告生成、培训完成或表格填写完成当作问题已关闭。
- 不得用网页 Profile、颜色或图表替代数据、证据和关闭条件。
- 不得把“第一性原理”“瓶颈”等分析标签直接写成没有数据支持的结论。
