# IPQC 过程质量分析 · 决策闭环版

先执行 quality-analysis-core，再执行本 Skill。只解释固定快照，不修改原始数据、统计口径或已确认事实。

## 1. 使用边界

本 Skill 是 quality-analysis-ipqc 的升级视角。它不是重算口径的引擎，而是把现有 IPQC 数据转成管理决策。

必须保留：

- 送检量是分母，不是质量结果；
- 异常数量、问题记录数、异常密度分开解释；
- 发现量增加不等于过程恶化；
- 组装人员只从 IPQC 的送检人读取，不得替换为检验人、检验员或判定人。

## 2. 管理决策页

正式报告第一屏必须先给出管理决策页，只回答六件事：

1. 当前最大问题是什么；
2. 这是质量恶化、检出增强，还是结构变化；
3. 瓶颈在公司、基地、工坊、交付经理、外包段还是自制段；
4. 如果本周期不处理，会造成什么业务损失；
5. 下一步最小验证实验是什么；
6. 谁负责、何时关闭、用什么证据关闭。

没有证据时写 待验证，不要用推断伪装事实。

## 3. 数据与证据双轴

至少核对：

- 送检批次或记录数
- 送检数量
- 异常数量
- 问题记录数
- 异常密度
- 基地
- 工坊
- 交付经理
- 机长
- 送检人
- 问题类型
- 日期
- 关闭状态
- 外包/自制
- 严重度（如有）
- 复检/关闭证据（如有）

每个关键结论同时写两轴：

- 数据可信度：A / B / C
- 结论成熟度：已证实事实 / 有证据推断 / 待验证假设

数据可信度 A 只表示数据可审计，不表示根因已经证实。

## 4. 第一性原理与业务损失桥梁

把异常多拆成可计算事实：

1. 先定义边界：公司 → 深圳/杭州基地 → 工坊/交付经理；
2. 再找可达基准：同周期、同基地、同工坊、同机制的最好稳定表现；
3. 再算差距：当前值、基准值、差值、分子、分母、样本量、周期；
4. 再拆机制：标准、首件、自检、送检、反馈、纠正、复检关闭；
5. 最后连到业务后果：返工、停线、交期、重复送检、工坊负荷、客户逃逸风险。

如果无法量化金额，就量化为异常次数、重复次数、逾期数、影响工坊数、影响基地数。

## 5. 双重 Pareto

必须同时做三层 Pareto：

- 组织 Pareto：基地、工坊、交付经理；
- 机制 Pareto：异常类型、工序、设备、工装、材料、工艺；
- 交叉 Pareto：高风险工坊/交付经理 × 重复失效机制。

排序不能只看异常数量，必须同时看：

- 异常密度
- 送检量
- 重复问题
- 未关闭或逾期问题
- 严重度
- 影响范围

如果数据不足，明确降级排序依据，不得强行排名。

## 6. 风险判断

沿以下链路分析：

作业标准 → 组装 → 首件/自检 → 送检 → 异常反馈 → 纠正 → 复检关闭

重点识别：

- 跨人员、跨机长、跨工坊重复问题；
- 外包与自制差异；
- 换线或参数变更；
- 设备工装材料共因；
- 异常放行；
- 无复检证据关闭。

多人共享问题优先作为过程或管理机制假设，不直接归责个人。

## 7. 根因最小验证实验

第一性原理不是列更多原因，而是用最小实验排除最多假设。每个 TOP 问题必须输出：

问题 | 根因假设 | 最小验证动作 | 数据来源 | 判定标准 | 单一Owner | 截止日期 | 结论状态

验证动作只写可执行动作，例如：

- 抽查标准版本、首件记录、自检记录、工装防错状态
- 比较外包/自制同机制异常与关闭证据
- 按周复核异常密度、重复问题和逃逸

验证前只能称假设或推断；验证通过后才能写已证实根因。

## 8. 行动与证据闸门

每条行动必须包含：

- actionId
- 阶段
- 问题或结论编号
- 单一 Owner
- 协同人
- 截止日期
- 复查日期
- 交付物
- 验收指标
- 关闭证据
- 升级条件

按周期组织：

- 0—30天：隔离重复异常、清理逾期及无复检证据问题；
- 31—60天：固化标准、首件、自检、工装防错、参数控制和异常升级；
- 61—90天：验证异常密度、重复问题、逾期问题是否下降，并横向展开到相似工坊。

没有交付物和验收指标，不得因为开过会或写过报告而关闭。

## 9. IPQC 组织主线

公司级复盘主线固定为：

公司 → 深圳/杭州基地 → 工坊/交付经理

向下追溯时可用供应链映射表到机长和送检人，但模块报告不要复制角色 Agent 的个人明细。

## 10. 输出约束

正式报告必须先给：

1. 数据审计、口径和证据双轴；
2. 一页管理决策页；
3. 公司 → 基地 → 工坊结果与趋势；
4. 业务损失和数据缺口；
5. 组织、机制和交叉 Pareto；
6. TOP 问题、过程断点、约束和最小验证实验；
7. 单一 Owner、30/60/90 天行动与证据闸门；
8. 待补数据、管理决策请求和复查日期；
9. 审计附件；
10. 文末机器图表契约。

## 11. 视觉契约

正式报告正文必须是人读版，不得写出“REPORT_VISUAL_SPEC_JSON”标题、代码说明或机器字段说明。若需要图表契约，末尾只直接追加遵循 skills/quality-analysis-core/references/report-visual-contract.md 的 reportKind 为 module 的 REPORT_VISUAL_SPEC_JSON 数据块，由渲染器隐藏消费。

IPQC 优先输出：

- 送检量和异常密度趋势
- 基地或工坊比较
- 外包与自制对比
- 问题类型 Pareto
- 工坊与问题交叉图
- 内外包构成变化堆叠图
- 异常变化拆解瀑布图（仅在增减贡献可以被数据拆开时）

图表能表达的内容不要重复放表格；表格只保留证据和行动台账。

“过程断点与改进重点”要用管理语言而不是推演语言：

- 先写客观数据和业务影响；
- 再写当前最可能的过程断点；
- 再写最小验证动作；
- 再写责任人与关闭门槛。

除审计附件外，正文不逐条展示 `S/M/O/C/X` 证据编号，只保留证据等级和结论编号。

## 12. 完成标准

成功标准不是写完报告，而是：

- 决策已作出；
- 验证已定义；
- 责任已唯一化；
- 关闭条件可审计；
- 同类问题不再重复发生。
